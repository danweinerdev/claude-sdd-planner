## Spec-Driven Development

Planning artifacts live at `{{PLANNING_ROOT}}/`, configured by `planning-config.json`. Use the installed `sdd-planner` skills for research, specifications, designs, plans, implementation, review, debriefs, and validation.

Each plan's decisions live at `Plans/<Name>/<Name>-Decisions.json`, append-only. The only write path is `sdd decide add --plan <Name> --statement "..."`, run only after the user approves the exact statement; reads (`sdd decide list|current|lookup`) are always derived. Never hand-edit a `-Decisions.json` file directly.

Keep artifact status in YAML frontmatter. Plan and implement each task as one clean, complete, independently bisectable native SCM revision/checkpoint; subtasks are mechanical steps inside that boundary. Review each task's complete diff before finalizing that revision and preserve complete task state in the lifecycle record. Update task status and subtask checklists only after verification commands have actually run and the task's completion-evidence section records exact commands/tools, context, revision/checkpoint, result, and observable evidence. Write artifacts in-flow when facts are known; this never implies an immediate commit. Plan-decision writes are the exception: never write one without the user's explicit approval of the exact, unmodified statement, shown in full first. **Git adapter:** in commit-capable workflows where commits are authorized, commit the verified feature slice first, then record lifecycle state once per affected root at phase close—never at task closeout, never per edit, amendment, or decision, never as intermediate SDD-only commits. Shared-root artifacts and decisions files use one boundary commit; external roots record once at the same boundary. The same per-root rule applies to a contiguous spec/design/plan session under the plugin's `shared/autonomy.md` SCM cadence. A phase's history should read as one lifecycle commit, N implementation commits, one lifecycle commit. Dirty or no-SCM work remains non-complete. Phase completion requires aggregate evidence plus a persisted, frozen, final `Aligned` run of all four `sdd-code-review` lanes. Material changes after review require a fresh full run. Before implementation, read the active plan and phase; after material changes, run the `sdd-code-review` skill.
