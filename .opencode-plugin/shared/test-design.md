# What Makes a Test Good

## Purpose

This is the design standard for improving test generation: choose useful tests **before implementation**, then collect enough evidence to trust them **without redundant proof work**. It applies to human- and agent-authored tests.

**A good test exercises a meaningful contract through real behavior, distinguishes a relevant defect from a correct implementation, and produces a trustworthy, understandable result at an appropriate cost.**

Passing is an observation, not a quality rating. A test can pass because it asserts the wrong thing, mocks away the subject, never runs, or duplicates coverage. Failing is not automatically useful either: a broken fixture says nothing about the intended behavior.

This guide governs test-design judgment. It does not waive existing execution, hazard, review, or completion gates. In particular, a hazard-discharging test still requires recorded red evidence before green can count. Recommendations here are not claims that the current generator or validator already enforces them.

## 1. Start with an obligation, not a test name

Before generating a test, answer:

- **What must be true?** State an observable behavior or invariant.
- **Why must it be true?** Identify the requirement, public contract, design constraint, or reproduced defect that establishes it.
- **What could be wrong?** Name a plausible fault that matters to that obligation.
- **What already covers it?** Inspect existing tests and explain the gap or deliberate strengthening.

“Test the parser” is a topic. “Duplicate keys are rejected with the offending key identified, and no partial configuration is published” is a contract.

Do not invent requirements to fill a template. An ambiguous expected result is a question to resolve, not an invitation to guess. A source citation explains why work exists; the test must also show how its stimulus and assertions establish that obligation.

## 2. Ground the subject, setup, and expected result

### Real symbols and feasible setup

Inspect the actual entrypoint, collaborators, fixtures, framework, and test-discovery conventions. Every referenced project symbol must exist, be generated by a known build step, or be deliberately created as part of the change. In TDD, a minimal stub may establish the planned interface; do not reference an imaginary implementation or overwrite working code with a stub.

Confirm that the fixture reaches the intended path. For example, a fake dependency installed under the wrong lookup key may never be used; a permission change may not deny access on the target operating system. When the test depends on injection, establish that the injection took effect.

If no controllable test seam exists, identify the necessary engineering work before promising the test. Investigate or split the work rather than leaving the implementer to discover an impossible setup.

### A defensible oracle

An **oracle** is the rule used to decide whether the observed result is correct. It may be a specified value, state transition, error, invariant, independent reference, or relationship between executions.

- Derive expectations from an identifiable contract. For new behavior, the requirement—not the unfinished implementation—defines the answer.
- Do not compute the expected result by calling the same logic being tested or copying its algorithm into the test. Shared mistakes can make both sides agree.
- Observed output or existing source can ground a **characterization test** that preserves current behavior. Label that purpose: recording what exists does not establish that it is what should exist.
- Keep characterization tests as regression protection while that behavior matters. When its intended contract is resolved or deliberately changed, review the expectations against that authority; retain, replace, or retire them explicitly rather than freezing accidental behavior forever.
- Use tolerances only when the contract permits approximation. Make their meaning explicit; do not widen them until failures disappear.
- Review golden files and snapshots against the contract. Updating a snapshot is accepting new expected behavior, not merely repairing a failing test.

## 3. Assert the behavior that matters

Exercise the subject's supported interface, not private implementation structure by default. Assert returned values, externally observable state, permitted effects, and forbidden effects as the contract requires. Tests should survive internal refactoring that preserves behavior.

| Weak evidence | Stronger evidence when required by the contract |
|---|---|
| The result is non-null. | The result contains the required values and excludes prohibited data. |
| Some exception occurred. | The intended operation produced the specified failure category and preserved required state. |
| A save method was called. | The correct entity was saved with the required identity, contents, and multiplicity. |
| A write returned an error. | The prior value remains readable and unchanged; no partial replacement became visible. |
| Two operations finished. | Their result satisfies the required ordering, atomicity, or consistency invariant. |

The stronger assertion is not always the more detailed one. Assert exact messages, call order, internal counts, or timing only when those details are contractual. Existence alone is sufficient when existence is genuinely the obligation.

Keep one coherent behavior per test, with as many assertions as that behavior needs. “One behavior” does not mean “one assertion.” Avoid tests that combine unrelated failures into a single difficult-to-diagnose result.

## 4. Keep the real subject in the test

Use controlled doubles for collaborators when necessary, especially network services, clocks, randomness, and operating-system effects. Never replace the subject itself with a mock and claim to have tested it.

- Prefer real, inexpensive domain objects to mocks of internal implementation details.
- A repository test must exercise repository behavior. A mock returning configured rows does not establish persistence or query correctness.
- An in-memory substitute proves only the semantics it actually shares with the real dependency. Use integration tests for transactions, locking, serialization, or other behavior it cannot represent faithfully.
- Interaction assertions are appropriate when the interaction is the contract. Otherwise, prefer the resulting behavior over evidence that an internal call happened.
- If fault injection is essential, verify the intended call or state boundary was reached. A failure in setup must not satisfy the assertion meant for the subject.

## 5. Select cases and test levels by risk

Start with a representative successful case, then add cases that distinguish materially different behavior. Consider these categories; apply them where relevant rather than generating a quota:

- **Equivalence classes:** representative inputs expected to behave alike, with meaningful exceptions separated.
- **Boundaries:** values just below, at, and just above a limit; empty versus absent; zero versus positive; minimum and maximum sizes.
- **Failures:** invalid input, unavailable dependencies, partial work, cancellation, timeouts, retry exhaustion, and recovery.
- **State transitions:** permitted and prohibited transitions, repeat operations, idempotence, and cleanup after failure.
- **Interactions:** ordering, concurrency, ownership, format compatibility, persistence, and externally visible side effects.
- **Security boundaries:** authorization, isolation, hostile input, and information that must not be disclosed.

Do not enumerate every combination when a few cases distinguish the relevant behaviors. Parameterize shared arrangements with meaningful case names. Use property-based or fuzz testing for broad input spaces, but give it a real invariant, relevant input generation, and reproducible counterexamples. Reproducible seeds do not replace exploration; retain important discovered failures as regressions.

Choose the cheapest level that can actually establish the claim:

| Level | Appropriate claim |
|---|---|
| Unit | Local decisions, calculations, transformations, and failure policy with controlled collaborators. |
| Component / integration | Real boundaries, adapters, storage, process behavior, or cooperating components that unit doubles cannot establish. |
| Contract / compatibility | Producer and consumer agree on supported protocol, schema, or version behavior. |
| End-to-end | A critical user journey works through the assembled system. |

Property-based testing and mutation testing are techniques, not substitutes for choosing the right level. Do not make every leaf test pay end-to-end cost. Conversely, do not call a mocked unit test proof of integration.

Coverage metrics help locate unexercised branches; they do not prove useful assertions. Test count, line coverage, mutation score, and diagram shape are not acceptance criteria on their own.

Include maintenance cost in test selection: setup complexity, failure diagnosis, environmental upkeep, and sensitivity to harmless changes. Simplify overlapping tests when the same guarantees can be preserved more clearly. Do not delete valuable coverage merely because maintaining it exposes difficult engineering work.

## 6. Separate three kinds of negative evidence

| Activity | Question it answers | Example |
|---|---|---|
| **Behavioral negative test** | Does the system handle a prohibited input or adverse condition correctly? | An unauthorized write is rejected and stored data is unchanged. |
| **TDD red baseline** | Does this test detect the behavior missing before implementation? | The newly specified operation fails its expected-result assertion before it is implemented. |
| **Sensitivity experiment** | Would this test catch a particular faulty implementation? | Disable the authorization guard and confirm that the rejection test fails. |

These may overlap, but none automatically substitutes for the others. A negative test can pass against a permissive implementation if it checks the wrong error. A red test can fail because a fixture is broken. A sensitivity experiment establishes discrimination against the chosen fault, not correctness against all faults.

### Proportionate confidence, not proof paperwork

For every test, answer **“What relevant defect would make this fail?”** This is a design check, not a requirement to run a mutation tool for every assertion.

Use the ordinary before-implementation red run when it already demonstrates the intended discrimination. Add a controlled sensitivity experiment when that run is insufficient—for example, a concurrency guard, security check, rollback path, or already-implemented hazard might otherwise appear covered without being exercised. Target the particular uncertainty; do not multiply experiments merely because several labels describe the same obligation.

Run destructive or guard-disabling experiments only in isolated, disposable test state. Restore the correct implementation, then verify the final state. Never leave injected defects in the deliverable or affect production resources.

Reuse recorded evidence only when it remains applicable to the same test and obligation under the governing workflow. An unchanged name is not proof of unchanged assertions, setup, or semantics. Do not fabricate red history, duplicate reports to imply additional runs, or bypass a mandatory gate. Summarize the fault and observed result once; link the real report instead of producing a separate essay for every test.

## 7. Use red–green–refactor as an engineering loop

1. **Establish a usable baseline.** Verify the framework can discover and execute the selected tests. Separate existing failures from failures introduced by this work.
2. **Write the smallest meaningful test first.** Arrange the relevant state, exercise the real subject, and assert the specified outcome. Keep setup, action, and assertions distinguishable.
3. **Observe and explain RED.** The selected test must execute and fail for the intended reason. Missing tools, syntax errors, accidental import failures, and unrelated fixture failures are not behavioral RED. Deliberate compile-rejection tests are different: compiler diagnostics are their oracle, and the test harness itself must execute successfully.
4. **Implement GREEN.** Make the smallest complete change that satisfies the contract—not a hardcoded answer that merely fits one example. If the examples admit an obviously wrong shortcut, strengthen the cases or oracle. Do not weaken expectations to obtain a pass. Correct a wrong test only against evidence of the actual contract.
5. **Refactor while preserving behavior.** Improve structure with the tests still passing. New validation, new errors, or changed side effects are new behavior, even if existing tests miss them; give them a justified test-first cycle.
6. **Check the affected integration.** Run the selected tests and appropriate surrounding regressions. Preserve required broader gates; a fast local pass is not a replacement for them.

A new test around existing correct behavior may pass immediately. Classify it as characterization or coverage strengthening rather than pretending an implementation cycle occurred. If a red observation is mandatory for its hazard or workflow, produce an appropriate controlled baseline through the supported process; this classification grants no exemption.

## 8. Make results reproducible and diagnosable

Tests should own their state and clean up their resources. They must not depend on execution order, a developer's configuration, credentials, live services, locale, timezone, or ambient filesystem contents unless that dependency is intentional and provisioned explicitly.

One test's mutations must not leak into another through global variables, environment settings, shared databases, files, or background work. Restore changed process-wide state and isolate or serialize tests that cannot safely share it; cleanup after a test does not make concurrent interference safe.

- Control clocks and randomness where relevant; record seeds and minimized failing inputs for generated cases.
- Coordinate asynchronous tests with observable events, barriers, or readiness conditions instead of guessed sleeps. Apply deadlines to prevent hangs without asserting an arbitrary machine-speed threshold.
- Verify the actual invariant in concurrency tests. Merely running operations in parallel does not prove that they overlapped at the vulnerable boundary.
- Use platform-appropriate fixtures and verify their preconditions. Unsupported capabilities are explicitly reported, not silently counted as passing tests.
- Give failures names and messages that identify the case, expected outcome, actual outcome, and relevant context. Retain enough evidence to reproduce the failure without exposing secrets.

Do not retry flaky tests until green and discard the failed attempts. Diagnose nondeterminism. A quarantined test remains a visible coverage gap, not a passing guarantee.

## 9. Require evidence that the intended tests ran

A successful runner process is not sufficient. Confirm the intended test identities were discovered and executed, and derive outcomes from actual runner output or structured reports.

- Zero executed selected tests, unexpected skips, unresolved identities, or unparseable results do not establish success.
- Distinguish assertion failure, compilation/setup failure, timeout, crash, and incomplete output. Do not let “some failure” satisfy a specific negative expectation.
- Bind evidence to the tested candidate and relevant command/configuration. Do not relabel an old report as a run against changed code or tests.
- Report partial results as partial. A truncated report, interrupted run, or unexplained test-count mismatch is not a complete pass.

A useful record identifies the package-qualified selected tests, repository-owned runner identity, tested candidate, observed failure or pass, and native report containing that evidence. Capture mechanical execution and content-binding metadata contemporaneously with repository tooling; a model must not reconstruct output, exit status, or snapshots afterward. Evidence validators check supplied facts but do not thereby own or perform test execution. Narration does not substitute for execution.

## 10. Example: the error is not the whole contract

Suppose a contract requires division by zero to raise `InvalidInput`, while valid division returns the quotient.

**Weak:** call `divide(5, 0)` and accept any exception. An implementation with no validation may still throw an arithmetic exception and pass this test.

**Better:** require `InvalidInput` for a zero denominator and verify representative valid quotients separately. Removing the validation guard should fail the specific error assertion; throwing `InvalidInput` for every input should fail the valid cases. Do not require exact error-message wording unless the public contract requires it.

The same reasoning applies to persistent writes. “The write failed” does not establish atomicity. If the contract promises failure leaves prior data intact, inject a fault at the relevant write boundary and verify the old data is still readable and unchanged, with no partial replacement visible. A double that fails before the real write path is entered cannot establish that guarantee.

## 11. The generation workflow

Use this compact design card before dispatching implementation. It may live with the existing task or payload; it is not a new tracking system or a separate document required for every test.

```text
Behavior and source: the obligation and its authority
Risk and level: the relevant failure mode and why this test level is sufficient
Existing coverage: the gap or deliberate strengthening
Cases and oracle: representative stimulus -> observable expected outcome
Subject and seam: real code exercised, collaborators, fixtures, and missing setup
Red and sensitivity: expected red reason; extra experiment only where needed
Execution: test identities, targeted command, and where evidence will be recorded
```

**Generate in this order:** inspect intent and code → inventory existing coverage → design the cases and oracles → resolve missing seams → author tests → verify discovery and intended RED → implement and verify GREEN → refactor → run affected regressions.

When a test is already good and adequate, reuse it. When a proposed test cannot be grounded, investigate rather than invent it. When test design exposes a missing engineering obligation, reconcile that obligation with the specification or design before quietly adding implementation scope.

## 12. Review and acceptance checklist

A reviewer should be able to answer **“Why this test, why this assertion, and why at this level?”** without reconstructing the author's intent.

- [ ] The behavior matters and its expected outcome has an identifiable authority.
- [ ] The subject, fixtures, and injected conditions are real and reach the intended path.
- [ ] Assertions distinguish a relevant defect from correct behavior without copying implementation logic or overfitting internals.
- [ ] Important success, boundary, failure, and integration cases are covered or have explicit risk-based exclusions.
- [ ] The test adds value beyond existing coverage and uses an appropriate execution level.
- [ ] Required RED evidence is the intended failure; extra sensitivity work addresses a named uncertainty rather than a quota.
- [ ] State, scheduling, dependencies, and cleanup are controlled sufficiently for a reproducible result.
- [ ] The intended tests actually ran against the recorded candidate; skips and incomplete evidence are not presented as passes.
- [ ] Refactoring preserves the contract, and newly discovered behavior is not hidden inside cleanup.

**Reject or rework** invented symbols or expectations, mocked-away subjects, vacuous assertions, unjustified duplicates, accidental RED, and claimed passes without execution evidence. Do not improve a score or satisfy a graph field at the expense of the guarantee the test exists to protect.
