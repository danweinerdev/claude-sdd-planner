# SDD Toolchain — Single Go Binary, Artifact Compiler, and Validator

## Overview
Replace the plugin's Python scripts and shell hooks with one cross-platform Go
executable, `sdd`, that owns every mechanical operation on SDD artifacts:
validation, artifact construction, frontmatter and identifier management,
cross-document linkage, status transitions and their gates, and the plugin's
Claude Code hooks.

The toolchain has two layers, delivered in that order:

1. **Validation parity.** Port `scripts/sdd_validate.py` and
   `scripts/sdd_decision_validate.py` into `sdd validate` and
   `sdd decide validate`, preserving every deterministic contract except a
   closed set of named deltas, proven by a frozen differential corpus before
   Python is removed.
2. **The artifact compiler.** Add `sdd apply`, which accepts a Markdown
   *proposal* on stdin and emits the artifact itself — parsing against a
   declarative per-type schema, allocating identifiers, resolving references,
   normalizing output, and stamping tool-owned frontmatter. A `PreToolUse` hook
   then denies direct `Write`/`Edit` on artifact paths, making the compiler the
   only writer of anything another document can reference.

The design principle for layer 2 is **the model authors content; the tool commits
it**. Prose is opaque payload the tool never composes and never interprets
semantically. Structure — headings, frontmatter, identifiers, references, status
— is tool-owned and inviolable. This converts the plugin's largest current
failure mode, silent structural drift caught after the fact by a validator, into
loud construction-time refusal in the same turn.

This spec **supersedes `Specs/Go-Validator`** and carries its requirements
forward. The two intentional bug fixes, the documented path-resolution
correction, the parity and branch-manifest gates, and the normative test
manifest are preserved with their substance intact. The superseded spec's
two-executable command surface and ten-binary packaging are replaced by a single
`sdd` binary across five OS/architecture targets.

## Goals
- Depend on one self-contained `sdd` executable for Windows, macOS, and Linux, installed by the user with `go install`, requiring no Python, shell, PyYAML, or package manager at run time. Maintainer release tooling may retain Python; users never need it.
- Preserve every deterministic validation contract through a frozen differential corpus, then delete Python and PyYAML.
- Make artifact structure correct by construction rather than correct by post-hoc detection.
- Declare each artifact type's structure once, as data, and generate the templates, parser rules, apply behavior, and help text from it.
- Let lifecycle skills carry role and judgment instead of transcribed document-formatting procedure.
- Keep prose authorship, and only prose authorship, with the model.
- Fix planning-root-relative `related` resolution and support letter-suffixed task identifiers.

## Non-Goals
- Add semantic or model-judgment checks to any deterministic subcommand; reviewer agents keep every judgment duty they have today.
- Author, rewrite, summarize, or evaluate prose. The compiler is opaque to what a section says.
- Convert artifact bodies to YAML, JSON, HTML, or any other structured container. The frontmatter-plus-Markdown split is retained deliberately: structured data goes in frontmatter where machines consume it, and reasoning stays in Markdown prose where authoring quality and reviewer comprehension are highest.
- Integrate an external issue tracker. Frontmatter remains the only work-tracking layer (D-0010 stands); it gains a compiler, not a replacement.
- Execute commands recorded in completion evidence.
- Build a general Markdown formatter, or reformat any file that is not a schema-recognized SDD artifact.
- Redesign artifact, evidence, review, or decision-ledger schemas beyond the task-identifier grammar change in FR-13.
- Add SCM completion adapters beyond those the Python validator already supports.
- Build, download, self-update, or compile anything, at any time. The plugin never invokes `go`; provisioning is the user's `go install` per FR-41.
- Vendor, bundle, or commit prebuilt binaries to the plugin payload. Prebuilt distribution was considered and rejected for now (see FR-05); reintroducing it later is additive and changes no requirement here.

### Functional Requirements

#### A. Executable, packaging, and command surface

- **FR-01**: The plugin SHALL provide exactly one executable, `sdd`, built from one Go module. All functionality SHALL be reached through subcommands. This replaces the superseded spec's separate `sdd-validate` and `sdd-decision` executables; no functionality is delivered as a second binary.
- **FR-02**: The subcommand tree SHALL be `sdd validate`, `sdd decide {add,list,search,validate}`, `sdd apply`, `sdd section set`, `sdd show`, `sdd list`, `sdd next`, `sdd evidence add`, lifecycle transition verbs per FR-21, `sdd hook {pretooluse,sessionstart}`, `sdd version`, and `sdd doctor`. `sdd validate` SHALL preserve the full validator's current options and defaults (`--root`, `--scope`, `--format text|json`, `--identity-mode auto|current|historical`). `sdd decide validate LEDGER` SHALL preserve the focused validator's positional argument and options (`--format`, `--no-history`). Unknown options, missing values, invalid choices, extra positional arguments, and options belonging to a different subcommand SHALL print subcommand-specific usage to stderr and exit `2`. Canonically naming `sdd <subcommand>` in usage and invocation-error prefixes is an explicit compatibility delta from the Python script names.
- **FR-03**: Every subcommand SHALL use one exit contract: `0` for success, including a validation result whose only findings are `candidate` severity; `1` for authoritative findings or a refused mutation; `2` when the invocation is malformed or the operation could not run. `sdd apply` SHALL exit `1` on refusal and SHALL NOT have written any bytes.
- **FR-04**: Every subcommand SHALL support `--json`, emitting a stable machine-readable document with diagnostics carrying code, severity, path, line, message, correction, and implicated paths where applicable. Text output remains the default for `validate` and `decide validate` per FR-06.
- **FR-05**: (D-0015) The plugin SHALL NOT ship prebuilt binaries and SHALL NOT build them. `sdd` is provisioned by the user per FR-41. Every caller — lifecycle skills and hooks alike — SHALL resolve the executable through one ordered algorithm, defined once in `shared/path-resolution.md` and not re-derived per skill: (1) `${CLAUDE_PLUGIN_ROOT}/bin/sdd[.exe]`; (2) an `sdd` on `PATH`. A candidate is admitted only when its reported version satisfies the FR-38 floor; a candidate below the floor SHALL be rejected rather than used, because a binary predating a schema or CLI contract change silently applies the wrong rules. The first admitted candidate wins.

#### B. Validation parity (carried forward from the superseded spec)

- **FR-06**: For all behavior except the deltas enumerated in FR-07, `sdd validate` and `sdd decide validate` SHALL preserve each diagnostic's code, severity, path, line, message, correction, implicated paths, multiplicity, and deterministic sort order; and SHALL preserve normal and operational text and JSON response shapes, stdout/stderr routing, JSON key ordering, indentation, escaping, and trailing-newline behavior, so existing consumers parse results unchanged.
- **FR-07**: The complete set of intentional compatibility deltas is: FR-02 subcommand naming; FR-10 focused-ledger path aliases; FR-11 path-resolution conformance; FR-12 `related` resolution; FR-13 task-identifier grammar; and malformed-YAML parser prose under FR-09. No other difference from the Python oracle is permitted, and a parity fixture SHALL NOT be normalized away by citing anything outside this list.
- **FR-08**: Full-artifact mode SHALL preserve discovery, parsing, common schema, required-heading, stable-identifier, artifact-specific, hierarchy, citation, dependency-graph, traceability, decision-link, completion-evidence, review-gate, repository-identity, and lifecycle-durability checks represented by every `SDD` code and emission branch in the source-derived diagnostic manifest. Focused-ledger mode SHALL preserve canonical-ledger and archive discovery, parsing, schema, sequencing, supersession, collision-candidate, Git immutability, and concurrent-edit checks represented by every `DLG` code and branch. Numeric gaps in either series are unused or reserved, not implied diagnostics.
- **FR-09**: YAML handling SHALL preserve the two current parsing contracts: full mode's safe-load scalar behavior, and focused-ledger mode's duplicate-key rejection. It SHALL preserve relevant scalar types, date distinctions, source line marks, mapping/list/string distinctions, aliases and merge behavior, and the source spans used by lifecycle normalization. For malformed YAML the diagnostic code, severity, path, line, validation criterion, and correction SHALL remain stable, while parser-specific message prose MAY be normalized rather than reproducing PyYAML exception text byte-for-byte. Markdown inspection SHALL preserve visibility rules for HTML comments, fenced code, indented code, headings, sections, checkboxes, evidence labels and tables, citations, open questions, brainstorm baselines, justification phrases, and failing-evidence text; regex rewrites required by Go's engine SHALL be proven equivalent by shared fixtures, never assumed equivalent.
- **FR-10**: Internal artifact references and every diagnostic path SHALL use forward slashes on all operating systems. Planning-root artifacts use planning-root-relative paths; files in a configured repository use `@repo:<repository-key>/<repository-relative-path>`; the detected owning repository with no configured key uses `@repo:root/<repository-relative-path>`; a focused ledger outside known roots uses `@ledger/<path-relative-to-the-primary-ledger-directory>`. Native paths remain accepted as CLI input for roots, ledger arguments, working directories, and configured repositories, but SHALL NOT appear in diagnostics. These aliases intentionally replace the Python validator's machine-specific absolute paths. Git and SCM inspection SHALL preserve repository selection, exact revision grammar, ancestry and parent checks, staged and worktree comparisons, clean-worktree checks, linked-worktree behavior, lifecycle normalization, byte comparisons, and the current-versus-historical identity distinction; external commands SHALL be invoked without a shell. Scope handling SHALL preserve safe planning-root-relative input, direct file and directory forms, `/README.md` and `.md` alternatives, bare-name ambiguity reporting, plan ownership, transitive explicit `related` expansion, malformed-file diagnostics, and decision-diagnostic visibility. File discovery SHALL identify the same physical ledger only once on case-insensitive filesystems while preserving its on-disk spelling, and SHALL retain genuinely distinct case-variant ledgers where both can coexist.

#### C. Intentional corrections

- **FR-11**: Repository and planning-root resolution SHALL follow `shared/path-resolution.md`, including upward configuration discovery, relative or absolute `planningRoot`, and target paths from `planning-config.local.json`. This is an explicit documented-conformance delta: fixtures SHALL record both the Python validator's current incorrect lookup in committed `planning-config.json` and the expected local-config result.
- **FR-12**: A `related` entry SHALL be checked as a safe path from the already-resolved planning root, regardless of the invoking working directory and regardless of whether `planningRoot` is `.`, relative, or absolute. It SHALL resolve when the target is an existing discoverable artifact, Markdown resource, other file, or directory. Only discoverable SDD artifacts participate in transitive graph expansion, citation resolution, and `artifacts_in_scope`; a valid resource reference proves existence but is not reported as a validated artifact. A regression fixture SHALL reproduce the four false positives from `Plans/ArkPlatformV2/03-OrganizationManagement.md` — `Resources/UI-Redesign-Handoff/README.md`, `Resources/UI-Redesign-Handoff/ark-product-portal.md`, `Resources/UI-Redesign-Handoff/ark-product-manager.md`, and `Resources/design_handoff_ark_web_redesign/screenshots/product-portal` — with `planningRoot: .plans` invoked from the repository root, and SHALL cover `.`, relative, and absolute planning-root forms. Missing targets and paths escaping the planning root still emit `SDD041`.
- **FR-13**: Task identifiers SHALL use the owning phase, a dot, a decimal task number, and an optional single lowercase ASCII letter suffix: `<phase>.<digits>[a-z]?`. `3.1`, `3.1a`, and `3.2b` SHALL be valid and MAY coexist as independent tasks; no parent/child, replacement, sequence, or gap semantics are inferred from a shared numeric stem. Exact identifiers remain append-only and unique within a plan. Identifiers assigned to another phase or outside this grammar SHALL continue to emit `SDD064`. Dependency, heading, citation, evidence, history, review, sorting, and lifecycle logic SHALL treat each value as one exact opaque identifier. The `/plan` workflow, `shared/templates/plan-phase.md`, `shared/frontmatter-schema.md`, `agents/plan-reviewer.md`, and diagnostic correction text SHALL document this grammar; `/plan` SHALL run scoped validation after authoring or revising task identifiers and stop before reviewer dispatch on invalid or duplicate values. Suffix selection is an authoring choice, not a deterministic allocation algorithm, so FR-20 SHALL accept an explicit suffix rather than generating one.

#### D. Schema as data

- **FR-14**: Each artifact type SHALL be declared in exactly one machine-readable schema document, embedded in the binary at build time. A schema SHALL declare: required and optional headings with their order and nesting depth; frontmatter fields with type and **ownership** (author-supplied versus tool-owned); identifier namespaces and grammars; referential rules; status values and the gate each transition requires; and which sections are free-prose per FR-19.
- **FR-15**: The embedded schemas SHALL be the single source for the parser's rule set, `apply`'s allocation and refusal behavior, the generated contents of `shared/templates/`, and every subcommand's help text. Templates SHALL be generated rather than hand-maintained, and `make test` SHALL fail on any drift between a committed template and its schema-generated form. The **first** generation pass SHALL be byte-identical to the currently committed templates, so that FR-15 initially proves the generator reproduces reality rather than silently changing it. Rationale: the FR-31 frozen oracle fixtures are built from today's templates and are the entire safety argument for deleting Python under FR-33, so a generator that altered template bytes would leave those fixtures asserting content the plugin no longer produces — a divergence that would surface only after the deletion became irreversible. Any subsequent intended template change SHALL be an explicit, separately-frozen delta recording both old and new expected output, the same discipline FR-07 applies to parity deltas.
- **FR-16**: A project MAY supply schema overrides on disk, layered over the embedded defaults. An override MAY add optional sections, optional frontmatter fields, and project-specific referential rules. An override SHALL NOT remove a plugin-required heading, relax an identifier grammar, weaken a status gate, or reassign a tool-owned field to author ownership; each such attempt SHALL be a load-time error naming the rejected rule. An override SHALL NOT affect which paths are recognized as artifacts: the set of guarded paths is plugin-owned and derived from the embedded schemas only. Rationale: FR-28's write guard denies `Write`/`Edit` on schema-recognized artifact paths, so an override that could narrow path recognition would let a project silently re-open direct writes and disable the guard by configuration.

#### E. The artifact compiler

- **FR-17**: `sdd apply <artifact-path>` SHALL read a Markdown proposal from stdin and treat it as a proposal, never as the file. The bytes written SHALL be those the tool emits, produced in this order: parse the payload; match sections against the type schema; allocate identifiers; resolve references; normalize; stamp tool-owned frontmatter; write atomically. A payload that cannot complete every stage SHALL be refused whole, with all violations reported in one result rather than one at a time.
- **FR-18**: A tool-owned frontmatter field present in the payload SHALL be treated as a **verified assertion**, not a declaration — the same resolution FR-45 applies to identifiers, applied here because it is the same structural problem in a second place. Verification is against the artifact **on disk**, not against the value the tool would stamp: a payload value equal to the on-disk value is accepted and the tool still writes its own value; a payload value that differs SHALL refuse, naming the field and the subcommand that owns it; an absent field is accepted; and a tool-owned field present when no artifact exists on disk SHALL refuse, since there is nothing to verify against. `updated` SHALL always be stamped by the tool and never taken from the payload. Rationale, and why comparing against the stamped value instead of disk does not work: `updated` is restamped on every write, so it can never equal a fresh stamp, and a stamp-comparison rule would refuse every revision made on a later date than the original — which is every real revision. This preserves both halves of the original guarantee: a matching value is verified rather than honored, and a differing value refuses loudly rather than being silently discarded. `status` remains unchangeable through `apply`; FR-21's gated transition verbs are its only writer.
- **FR-50**: The FR-18 check additionally acts as a **stale-read tripwire** and SHALL be retained for that reason as well: when another writer has applied between a caller's read and its write, the on-disk `updated` has moved and the caller's payload value no longer matches, so the write refuses. This SHALL NOT be treated as a substitute for FR-48's digest precondition — two body-only edits on the same date leave `updated` identical, so frontmatter agreement does not imply the bytes are unchanged. Both checks are required: neither may be removed as redundant.
- **FR-19**: Section handling SHALL normalize where authorial intent is unambiguous and refuse where it is not. Auto-corrected: heading letter case, trailing punctuation, bold or emphasized text used where a heading is required, a heading nested one level off its schema depth, and list-marker style. Refused: a required section absent, a reference that does not resolve, two payload sections mapping to one schema slot, and any section not present in the schema. Every auto-correction SHALL be itemized in the result so the caller can converge. Additionally, every artifact type's schema SHALL designate at least one **free-prose** section — design rationale, alternatives rejected, or the type's equivalent — for which the tool creates the heading and applies no structural enforcement to the body beyond FR-22, because the value of that section is in its variance.
- **FR-20**: Identifier allocation SHALL be performed only by the tool, SHALL be append-only and monotonic within each namespace, and SHALL never reuse a retired value. `FR-NN`, `NFR-NN`, `AC-NN`, `D-NNNN`, `F-NN`, and `FU-NN` SHALL be allocated by the tool, and only for payload items that carry no identifier — an item that already has one is governed by FR-45. Allocation SHALL take the next value above the namespace's high-water mark and SHALL NOT fill gaps, so a retired identifier is never reissued. The high-water mark SHALL be computed as the maximum over live identifiers in the artifact, identifiers named in its retirement notes, and identifiers of that namespace cited in `related` artifacts. Task identifiers SHALL be accepted as explicit values validated against FR-13, since suffix choice is authorial. The result SHALL report every identifier allocated and the payload text it was bound to.
- **FR-45**: `apply` SHALL support revising an existing artifact, and identifiers in the payload SHALL be treated as **assertions the tool verifies**, never as declarations the author is inventing. Given an existing artifact: a payload item carrying an identifier that exists in the artifact keeps it unchanged; a payload item carrying an identifier that does not exist SHALL refuse, naming the identifier and listing the namespace's live values; a payload item carrying no identifier is new and is allocated per FR-20; and an identifier present in the artifact but absent from the payload SHALL refuse as an unintended retirement unless `--retire <id>` names it explicitly, in which case the tool writes the retirement note in the form `shared/frontmatter-schema.md` § Stable Identifiers prescribes. Rationale, and why identifiers must be present rather than stripped: requiring the author to omit them would force the tool to re-derive which payload item is which, and any mis-association silently re-binds live cross-document citations — the exact failure append-only identifiers exist to prevent. Keeping the retirement register in the artifact body, written by the tool, satisfies "never reuse a retired value" without adding a frontmatter field, which this spec's Non-Goals forbid.
- **FR-21**: Status transitions SHALL be dedicated verbs, each enforcing the gate its schema declares, evaluated by the same rule implementations `sdd validate` uses rather than a second copy. `sdd task complete` SHALL refuse without a conforming completion-evidence record; `sdd phase complete` SHALL refuse without a persisted, frozen, four-lane `Aligned` review; `sdd plan complete` SHALL refuse while any phase is incomplete. `sdd evidence add` SHALL record command, revision identity, and observable result as structured data. Refusals SHALL name the unmet gate and the artifact path and line proving it unmet.
- **FR-22**: `sdd section set <artifact-path> --heading <heading>` SHALL perform a single-section write through the same parser, lint, and normalizer as `apply`, leaving all other sections byte-identical and all frontmatter untouched except `updated`. Payloads to both `apply` and `section set` SHALL be linted to reject content that forges structure: frontmatter delimiters, and heading lines at or above the target section's depth for `section set`. Identifier handling in both is governed by FR-45 — an identifier that already exists in the artifact is permitted and preserved, and only an identifier with no counterpart on disk is rejected. A blanket rejection of identifier declarations SHALL NOT be applied, because an artifact's own live identifiers necessarily appear in any payload that revises it.
- **FR-23**: Prose SHALL be opaque except for one lexical check: identifier-shaped tokens SHALL be resolved against the artifact and its `related` artifacts, and an unresolvable citation SHALL refuse the apply. No comprehension of prose meaning is performed or implied. Three exemptions are required, each load-bearing: an identifier inside an inline code span or fenced block SHALL be treated as a literal and never resolved, giving authors a deliberate escape for hypothetical or illustrative values; a **retired** identifier SHALL resolve, since FR-20 guarantees retirements exist and rationale prose is expected to reference them; and a section the schema designates free-prose SHALL be exempt from resolution entirely. Rationale: FR-19 creates the free-prose section precisely so unconstrained reasoning has somewhere to live, and rejecting an apply because rationale named an unallocated or retired identifier would push authors to stop writing identifiers in prose — degrading the traceability the rest of this spec depends on.
- **FR-24**: `sdd apply --dry-run --diff` SHALL print the normalized result, every allocation, and every auto-correction, write nothing, and exit `0` when the payload would apply. Normalized output SHALL be byte-idempotent: applying an already-normalized artifact SHALL produce identical bytes and report no corrections. Writes SHALL be atomic via temporary file and same-directory rename, leaving no partial artifact on failure or interruption.
- **FR-25**: `sdd next --json` SHALL report the current state of a given plan or artifact, the next action its schema and gates require, and the literal subcommand invocation that performs it. `sdd show` and `sdd list` SHALL expose artifact state and collections without requiring a caller to parse Markdown.
- **FR-26**: `sdd decide add` SHALL be the only writer of the decision ledger. It SHALL perform the append-time collision check defined in `shared/decision-log.md`, and on a contradiction with an `accepted` entry SHALL refuse and exit `1` naming the colliding entry, never auto-resolving and never settling by recency. Accepted entries SHALL remain immutable except for `status` and `superseded_by`.

- **FR-48**: Every mutating subcommand SHALL be **isolated as well as atomic**. `apply`, `section set`, `evidence add`, `decide add`, and every lifecycle transition verb SHALL capture a digest of the artifact's bytes at read time and refuse the write when the on-disk bytes no longer match, with a distinct diagnostic instructing the caller to re-read and retry. Rationale, and why FR-24's atomicity is insufficient: `commands/implement/SKILL.md` launches a wave of `code-implementer` agents concurrently, and `code-implementer` is not among the seven read-only agents, so two agents recording evidence against the same phase document is the expected case rather than an exotic one. Temp-file-plus-rename makes each write indivisible but does nothing about the read-modify-write cycle around it, so the later rename silently discards the earlier agent's evidence — and the resulting `sdd task complete` refusal looks like a missing-evidence bug rather than a lost update. A caller MAY pass the expected digest explicitly for a read-then-write performed across turns.

#### F. Hooks and the write guard

- **FR-27**: (D-0013, D-0014) `sdd hook pretooluse` SHALL replace `hooks/reviewer-bash-guard.py` and `sdd hook sessionstart` SHALL replace `hooks/load-decisions.sh`, removing the plugin's Python and POSIX-shell runtime dependencies. The Bash guard's current behavior — the read-only `git`/`p4` subcommand allowlist, the write- and network-shaped denials, permitting test and lint runs, applying only to the seven read-only agents, and failing open for every other agent and the main session — SHALL be preserved exactly and proven by its own parity fixtures. `hooks/hooks.json` SHALL register both `${CLAUDE_PLUGIN_ROOT}/bin/sdd` and `${CLAUDE_PLUGIN_ROOT}/bin/sdd.exe` entries so that the absent one fails open on each platform, and SHALL rely only on `${CLAUDE_PLUGIN_ROOT}` interpolation — never on shell expansion of `$HOME` or a version string — which is why FR-37 requires the plugin-root copy.
- **FR-28**: `sdd hook pretooluse` SHALL additionally deny `Write` and `Edit` on schema-recognized artifact paths under the resolved planning root. It SHALL NOT deny `Read` under any circumstances; SHALL NOT deny non-artifact paths inside the planning root such as `notes/` or a planning-root `README.md`; and SHALL NOT deny plugin source in the plugin's own repository (`commands/`, `agents/`, `shared/`, `scripts/`, `hooks/`). Where the planning root cannot be resolved confidently, the guard SHALL fail open. Each denial message SHALL name the owning subcommand and a concrete runnable invocation for the blocked path.
- **FR-44**: (D-0014) `sdd hook pretooluse` SHALL treat `sdd` itself as a guarded command for the seven read-only agents, using the same allowlist discipline it applies to `git` and `p4`: read-only subcommands (`validate`, `show`, `list`, `next`, `version`, `doctor`, `decide list|search|validate`) are permitted, and every mutating subcommand (`apply`, `section set`, `decide add`, `evidence add`, and all lifecycle transition verbs) SHALL be denied. Rationale, and why this is required rather than optional: the current guard denies an enumerated set of command heads and permits unrecognized ones, so introducing a mutating CLI without allowlisting it would hand the read-only agents a sanctioned path to rewrite planning artifacts — a strictly larger hole than the `Write`/`Edit` denial in FR-28 closes. A new mutating subcommand added later without a corresponding guard entry SHALL fail the test suite, so the allowlist cannot silently fall behind the command tree.
- **FR-29**: Every refusal, denial, and usage error SHALL name the violated constraint and the correct form. Unknown flags SHALL emit a nearest-match suggestion; an unresolvable identifier reference SHALL list the identifiers available in the cited artifact; a schema mismatch SHALL name the expected heading and the payload line. These messages are the primary interface for an automated caller and SHALL be covered by golden tests.

#### G. Migration and sequencing

- **FR-30**: Before any Go validation logic is written, a source-derived manifest SHALL assign every Python diagnostic callsite a branch identifier formed from source file, enclosing function, diagnostic code, and callsite ordinal, with named variant identifiers for distinct conditional message templates at one callsite. Any intentionally unreachable or duplicate branch requires a checked-in exemption with rationale. Shared fixtures SHALL run against Python and freeze at least one valid case, one failing case, and every input boundary named by that branch's predicates. The migration gate SHALL fail on an unlisted source emission, a stale exemption, a duplicate branch row, or a branch without frozen Python output. The complete manifest, frozen corpus, source scan, and tests SHALL exist and pass in the first parent of the first native-SCM revision that adds Go validation logic, verified by a history-aware gate.
- **FR-31**: Every existing Python test method SHALL have exactly one traceable named Go test case in the checked-in parity manifest `current-test-coverage.csv`. Before Go validation logic begins, the six current Python test files SHALL be frozen as non-executable oracle-source fixtures with SHA-256 checksums, preserving every literal and generated subtest input. The manifest SHALL record each Python test's fully qualified name, helper or CLI path, direct or incidental coverage, expected diagnostic or helper result, and unchanged-or-approved-delta status. A mechanical AST-based inventory check SHALL fail on a missing current test, a changed checksum, a duplicate mapping, a missing Go case, or a Go case that omits a frozen subtest identifier or input.
- **FR-32**: The parity suite SHALL run the Python oracle and the Go candidate over shared black-box fixtures and compare exit code, stdout, stderr, parsed JSON, diagnostic order, line, path, multiplicity, severity, message, correction, and implicated paths, permitting a difference only where a fixture explicitly cites an FR-07 delta and freezes both old and new expected results. Dedicated compatibility corpora SHALL cover YAML, Markdown visibility, CLI output, path safety and ambiguity, Git history and worktrees, completion evidence, review artifacts, decision archives, case-sensitive and case-insensitive discovery, and filesystem names containing spaces and non-ASCII characters.
- **FR-33**: (D-0012) The Python validators are deprecated on arrival of the port and retained only as the parity oracle; deletion is gated on proven parity, not on a date. The artifact compiler SHALL NOT be implemented until FR-30 through FR-32 pass and the Python scripts, Python-only imports, PyYAML dependency, and virtualenv test bootstrap are removed. Rationale, and the reason this ordering is a requirement rather than a preference: the compiler's normalizer rewrites artifact bytes, which would invalidate the byte-level differential comparison the parity gates depend on. Frozen oracle outputs, equivalent Go tests, and black-box fixtures SHALL remain as the authoritative regression suite after Python is gone.
- **FR-46**: Normalization SHALL NOT rewrite a history-bearing artifact as a side effect. Before the compiler is enabled for any artifact type, the byte-sensitivity of every lifecycle-durability, completion-evidence, and review-gate check SHALL be determined and recorded — which checks compare artifact bytes, which compare recorded revision identity, and which would be disturbed by canonical reformatting. An artifact at `status: complete`, or carrying `frozen: true`, SHALL be refused by `apply` and `section set` with a diagnostic naming the freezing record, and SHALL be normalized only by the FR-47 migration.
- **FR-47**: Converting existing artifacts to canonical form SHALL be an explicit one-time migration per artifact type, never an incidental first write. Each migration SHALL: run `sdd validate` over the affected scope and record the result before starting; normalize every artifact of that type, including `complete` and `frozen` ones; land as its own scoped lifecycle revision containing no implementation or content change, per D-0008's separation of bookkeeping from work; re-run `sdd validate` and require an identical diagnostic set to the pre-migration run, with any difference stopping the migration for the user; and re-anchor or re-record any identity that the FR-46 determination found byte-sensitive. The migration for a type SHALL complete before the FR-28 guard is enabled for it, so that no artifact is guarded while still non-canonical.
- **FR-34**: Every existing artifact under the repository's own planning root SHALL pass `sdd apply --dry-run` with normalization deltas only and zero refusals, proven by a corpus test. Where an existing artifact cannot be accepted, either the schema is wrong or the artifact is genuinely invalid; the resolution SHALL be recorded per artifact rather than resolved by loosening the schema wholesale.
- **FR-35**: The migration SHALL update every plugin command, shared convention, template, agent definition, Make target, dependency declaration, and maintenance document that invokes Python, names PyYAML, documents a removed entry point, instructs `Write` or `Edit` on an artifact path, or constrains validator behavior. Repository search SHALL find no runtime invocation of either Python validator, no PyYAML dependency, and no instruction to write an artifact by any means other than `sdd`.
- **FR-36**: The compiler and its write guard SHALL be rolled out one artifact type at a time — `spec` first, then `plan` and `phase`, then the remainder — with the FR-28 guard scoped to only those types whose schema has landed *and whose FR-47 migration has completed*, so that a defective path rule affects one type rather than all of them and no type is guarded while still non-canonical.

- **FR-49**: Executable resolution per FR-05 SHALL be performed **once per session and cached**, and the cached result SHALL be reported by `sdd doctor` alongside the candidate evaluation. Probing a `PATH` candidate SHALL use a fixed, argument-free version invocation with a bounded timeout, and SHALL be attempted only after the plugin-owned `${CLAUDE_PLUGIN_ROOT}/bin` location misses. Rationale: with FR-41 making `go install` the only provisioning path, `PATH` becomes the primary discovery route rather than a rare fallback, so an uncached resolver would spawn a probe process on essentially every logical operation — defeating NFR-07's stated purpose, which is that routing mutations through the tool imposes no per-call latency cost, since NFR-07 measures the subcommand and not the resolution wrapper. `sdd` is also a short, generic name, so executing a `PATH` candidate is executing an unknown program; ordering the owned location first and bounding the probe limits the blast radius of a name collision.

#### H. Toolchain, build, and version lockstep

- **FR-37**: `/setup` SHALL place or refresh a copy of the resolved binary at `${CLAUDE_PLUGIN_ROOT}/bin/sdd[.exe]` on **every** run. Rationale: `hooks/hooks.json` can interpolate only `${CLAUDE_PLUGIN_ROOT}` and cannot resolve `PATH` — hook processes frequently run with a minimal environment in which `$GOBIN` is absent — so a hook trusting `PATH` would fail open silently while every skill kept working, a failure with no symptom. A copy SHALL be used rather than a symlink on Windows, where symlink creation requires elevated privilege. `${CLAUDE_PLUGIN_ROOT}/bin/` SHALL be git-ignored. No version-scoped binary cache is required: `go install` produces a single binary per machine, and the FR-38 floor removes any need for two versions to coexist.
- **FR-38**: `sdd version [--json]` SHALL report the version the binary was built at, from the FR-39 generated source. `.claude-plugin/plugin.json` SHALL declare `minSddVersion` — the oldest binary the plugin's skills and hooks can correctly drive. A resolved binary at or above that floor SHALL be admitted; one below it SHALL be rejected with an operational error naming the detected version, the required floor, and the exact `go install` command that satisfies it. Exact equality with the plugin's own `version` SHALL NOT be required. Rationale: most plugin releases change skill prose or documentation without altering the CLI or schema contract, so requiring equality would break every working installation on a wording fix — and because `go install` yields a single unversioned binary per machine, equality would additionally make two plugin versions unable to coexist.
- **FR-39**: `.claude-plugin/plugin.json` SHALL remain the single source of both version values. The binary's own version SHALL reach it through a generated, committed Go source file (e.g. `internal/version/version.go`) derived from `plugin.json`'s `version`, written by the existing `bump-version.py` and therefore updated by `make bump-patch`, `make bump-minor`, and `make bump-major` in the same commit and tag. `minSddVersion` SHALL NOT be modified by any `make bump-*` target: advancing the floor is a deliberate, separately-committed act performed only when the CLI surface, schema, or diagnostic contract changes. `make test` SHALL regenerate the version file and fail on any difference from the committed copy, and SHALL fail when `minSddVersion` exceeds `version` in the same `plugin.json`. Rationale, and why build-time `-ldflags` injection is insufficient: `go install` does not apply the plugin's link flags, and since FR-41 makes `go install` the only provisioning path, an ldflags-only version would report as unknown in every real installation, defeating the FR-38 floor check entirely.
- **FR-40**: `/setup` SHALL verify provisioning **first, before any filesystem mutation**, and SHALL stop the entire setup when it fails. In order: resolve a binary per FR-05; confirm it satisfies the FR-38 floor; place or refresh `${CLAUDE_PLUGIN_ROOT}/bin/sdd[.exe]` per FR-37; verify by running `sdd version` and `sdd doctor` through the plugin-root path specifically; and only then proceed to the remaining setup steps, reporting the resolved source path and version. `/setup` SHALL NOT compile, download, or install anything.
- **FR-43**: An absent `sdd`, or one below the FR-38 floor, SHALL stop `/setup` entirely. It SHALL NOT generate `planning-config.json`, bootstrap planning directories, create launchers, or perform any other mutation. Rationale, and why partial setup is worse than none: a planning root without a working `sdd` is a repository that looks configured and then fails at first authoring attempt, giving the user two problems to diagnose instead of one. The stop message SHALL distinguish *not found* from *below floor*, name the detected version and required floor where applicable, and give the exact `go install github.com/danweinerdev/claude-sdd-planner/cmd/sdd@v<version>` command. `/setup` SHALL be idempotent, so re-running it after provisioning completes normally. `/setup` SHALL NOT install a Go toolchain or invoke a package manager.
- **FR-41**: (D-0015) `go install github.com/danweinerdev/claude-sdd-planner/cmd/sdd@v<version>` SHALL be the **only** supported provisioning path, satisfied by the module path matching the repository URL and by `make bump-*` creating the matching `v<version>` tag. The user performs it before invoking the plugin. Three consequences follow and SHALL be honored: the Go toolchain and network access are the user's prerequisites at provisioning time and never the plugin's at run time; the binary is unversioned at `$GOBIN/sdd`, so exactly one exists per machine, which the FR-38 floor accommodates; and the plugin SHALL NOT wrap, re-invoke, or automate `go install` on the user's behalf.
- **FR-42**: Because no binary exists before `/setup` runs, the plugin SHALL define its unprovisioned state rather than leave it to chance. Both hooks SHALL fail open silently when no binary resolves, so a fresh install degrades to no ledger injection and no Bash guard rather than a broken session. Every lifecycle skill SHALL instead fail loudly, naming `/sdd-planner:setup` and the resolved-path attempts, and SHALL NOT fall back to authoring artifacts by `Write`/`Edit`, and SHALL NOT present model judgment as deterministic validation. A skill's own semantic review layer MAY still run when it is clearly labeled as semantic and does not claim to substitute for the deterministic checks — the prohibition is on misrepresenting judgment as mechanical verification, not on judgment itself. `sdd doctor` SHALL report, for each FR-05 candidate path, whether a binary is present, its version, and whether it is admitted or rejected and why. It SHALL additionally report **the hook static path as its own checked item**, distinct from the FR-05 candidates, because a resolvable binary and a working hook are independent conditions: skills resolve through the FR-05 order while hooks can only use the plugin-root path, so reporting only the candidate list would show a healthy system while both hooks were silently dead. When the hook path is missing, `sdd doctor` SHALL say so as a named defect and name `/sdd-planner:setup` as the remedy. Builds SHALL be reproducible with symbol and DWARF stripping and trimmed paths, embedding no absolute build-host paths.

### Non-Functional Requirements
- **NFR-01**: `sdd` SHALL have no runtime dependency on Python, a shell, PyYAML, or a package manager. Git or Perforce MAY be invoked only for checks that already depend on the detected SCM, and never through a shell.
- **NFR-02**: `sdd apply`, `sdd section set`, `sdd decide add`, `sdd evidence add`, and the lifecycle transition verbs are the only subcommands permitted to mutate state, and they SHALL mutate only the addressed artifact. Every other subcommand, including all validation and both hooks, SHALL leave artifact bytes, SCM status, index state, worktrees, configuration, and network state unchanged.
- **NFR-03**: `make test` SHALL cross-compile `sdd` for `windows/amd64`, `darwin/amd64`, `darwin/arm64`, `linux/amd64`, and `linux/arm64` as a **portability check**, not as a packaging step — nothing built for a non-host target is distributed. Successful compilation is the required check for non-host targets; it exists to catch build-tag, path-separator, and syscall regressions before a user on that platform hits them at `go install` time. Only the host-matching target is executed locally, and a foreign-platform binary SHALL never be executed during testing.
- **NFR-04**: `go test ./...` SHALL run the complete platform-independent suite from a clean checkout without Python, PyYAML, network access, or generated files outside the test temporary directory. `make test` SHALL remain the authoritative repository entry point: `go test ./...`, the differential suite while the oracle exists, template-drift checks per FR-15, every cross-compilation target as a portability check, and host-native execution against smoke and integration fixtures, failing clearly when the host is not a supported build target.
- **NFR-05**: Emitted artifacts SHALL use LF line endings on every platform, and every path written into frontmatter SHALL use forward slashes, so that a Windows-authored artifact is byte-comparable with a POSIX-authored one and produces no cross-platform diff churn. The parser SHALL accept CRLF and a UTF-8 BOM as input.
- **NFR-06**: All path, heading, and identifier matching SHALL be correct under both NFC and NFD Unicode normalization, and all path and process handling SHALL support spaces and non-ASCII characters without constructing shell command strings.
- **NFR-07**: `sdd apply` and `sdd validate --scope` on a single artifact SHALL each complete within 300 ms on a typical artifact on supported hardware, so that routing document mutations through the tool does not impose a per-call latency cost on lifecycle skills. This bound is **provisional pending measurement**: it is an unsourced target, and the first working binary SHALL replace it with a figure measured on named hardware, adjusted up or down as the measurement warrants rather than retained by default.
- **NFR-08**: A Go toolchain and network access are **provisioning-time prerequisites satisfied by the user outside the plugin**, via FR-41. They SHALL NOT become plugin dependencies: no subcommand and no plugin step SHALL invoke `go`, compile, or fetch, and `sdd` SHALL run correctly on a host where the toolchain is removed after provisioning.

## User Stories
- As a plugin user on Windows, macOS, or Linux, I want `/setup` to build one native tool for my machine so that I never install Python, PyYAML, or a shell to use the plugin.
- As a new plugin user without a Go toolchain, I want to be told exactly what to install and what command to run, rather than watching skills fail for reasons I can't diagnose.
- As an artifact author working through Claude, I want a malformed document refused in the same turn with the correct form named, instead of discovering the problem three steps later or not at all.
- As a plugin maintainer, I want every old test and diagnostic branch mapped to the Go suite so that a rewrite cannot silently drop validation behavior.
- As a plugin maintainer, I want artifact structure declared once so that templates, validator, and help text cannot drift apart.
- As a plan author, I want to split a task into `3.1a` and `3.1b` and get identifier feedback during planning so that separately verifiable work keeps a stable relationship to its original task.
- As an artifact author, I want `related` paths interpreted from the documented planning root so that existing artifacts are not falsely reported as missing.
- As a reviewer, I want normalized canonical output so that a diff between two artifact revisions shows semantic change rather than reformatting noise.
- As an automation consumer, I want stable output and exit contracts so that changing implementation language does not break repository tests or lifecycle commands.

## Constraints
- The Python implementation is the compatibility oracle only until the differential suite is complete; it is never shipped as a runtime fallback.
- The FR-07 delta list is closed. A parity failure may not be waived by citing anything outside it.
- Diagnostic identifiers remain stable: the two corrections update behavior under the existing `SDD041` and `SDD064` codes rather than minting replacements.
- Planning artifacts and diagnostics must not record credentials, private hostnames, usernames, or machine-specific absolute paths, per `shared/frontmatter-schema.md` § Sensitive Data.
- Tests requiring filesystem case sensitivity, Git, or a specific operating system must declare and verify that prerequisite rather than silently passing.
- The compiler must be additive to reviewer judgment. No structural enforcement may be presented as, or substituted for, a semantic review lane.
- Intent isolation for the four review lanes remains behavioral, enforced by curated inputs; nothing in this toolchain weakens or replaces it.
- A one-time `go install` is a prerequisite for plugin functionality, performed by the user before the plugin is invoked. This is a deliberate accepted regression from the plugin's current install-and-go behavior, taken to avoid committing per-release binaries to repository history and to keep the plugin out of the business of compiling; it is parity with other AI/LLM tooling that requires `go install`.
- Nothing works before the binary is provisioned and `/setup` runs. Every skill and hook must behave correctly in the unprovisioned state per FR-42, and that state must be tested, not assumed.

## Dependencies
- A Go toolchain and network access on every **user's** machine at provisioning time, meeting the minimum version declared in `go.mod`, used by the user's own `go install` and never invoked by the plugin. Maintainers additionally need a toolchain capable of cross-compiling the NFR-03 portability matrix.
- A Go module path equal to the repository URL (`github.com/danweinerdev/claude-sdd-planner`), and a publicly resolvable `v<version>` tag per release, for the FR-41 `go install` path to work.
- A Go YAML implementation proven against the PyYAML characterization corpus behind a compatibility value model; selection is a design decision, not an assumed compatibility claim.
- A CommonMark parser exposing an AST with source positions, required for FR-29's line-accurate messages.
- Git for Git-specific integration tests and runtime identity checks.
- GNU Make or a compatible `make`.
- Python on **maintainer** machines only, for `bump-version.py` and the FR-39 generated version file. This is deliberately not ported into `sdd`: doing so would require `sdd` to exist in order to cut an `sdd` release, adding a bootstrap dependency for no user-visible benefit. No user-facing path invokes Python.
- `Specs/Go-Validator`'s normative parity manifest `current-test-coverage.csv`, carried forward into this spec's directory.
- Claude Code's hook JSON protocol, which must be pinned with a version and as-of date in the design before FR-27 and FR-28 are implemented.

## Open Questions
- **Resolved — payload growth.** Prebuilt bundling is rejected for now: five targets at roughly 10 MB each would add about 50 MB of incompressible blobs to repository history per release, and Claude Code installs plugins by cloning. The build-at-setup requirement in FR-40 and the `go install` fallback in FR-41 are the accepted cost, with the accepted worst case being parity with other AI/LLM tooling that requires `go install`. Prebuilt distribution remains viable as a later additive change — it would relax FR-40, not contradict it — if the toolchain prerequisite proves too costly for users.
- **What is the minimum Go version?** `go.mod` must declare it, and under FR-41 the user's own `go install` enforces it with Go's native error message rather than the plugin checking. The value depends on the YAML and Markdown libraries the design selects. **Non-blocking**: the requirement is that `go.mod` declares one, not what it is.
- **Resolved — the plugin never builds or installs anything.** `go install` performed by the user is the only provisioning path (D-0015, FR-41); `/setup` verifies and copies, and stops with an actionable message otherwise (FR-43). This also dissolves the module-fetch-needs-network problem: the network requirement now belongs to a step the user invokes explicitly, with Go's own diagnostics.
- **Does `apply` need a structured payload form in addition to Markdown?** A machine caller such as the `sdd-dashboard` plugin might prefer submitting fields directly. Leaning no for v1: Markdown-only keeps one parse path and one set of failure modes. **Non-blocking**: adding a second input form later is additive and changes no requirement stated here.
- **Should `windows/arm64` join the target matrix?** Excluded from NFR-03 today, matching the superseded spec. **Non-blocking**: adding a target is a build-matrix change with no behavioral requirement impact.
