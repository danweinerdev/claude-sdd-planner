# Fork-Aware Decision Ledgers

## Overview
Allow a repository to explicitly select a fork decision ledger through its existing `planning-config.json`. Store the selected ledger under its planning root, internal or external, retaining inherited ledger history unchanged and recording approved downstream differences separately. Repository configuration selects authority; planning-root storage does not imply cross-repository global authority.

For in-repository planning, the intended layout is the existing `Decisions/decisions.md` and `archive-*.md` plus a selected sibling `Decisions/fork.md`. For external planning, the same declaration selects a repository-specific ledger in the external planning root. No additional repo-root ledger, selector, generation directory or `.sdd/` tree is required. An external ledger is independently versioned planning history, not falsely described as versioned in the source repository merely because that repository points to it.

The motivating case is a downstream sdd-planner copy that needs a complete local replacement of a SDD-Toolchain:pd-f4a8d1a2-shaped provisioning decision while retaining its other obligations. This feature does not perform or authorize that repository/module migration. A fork declaration is not blanket permission to ignore inherited constraints.

### Baseline and terminology
Implementation context was inspected at revision `7cf2572f6eff929e1ea3eedd7604b74a1179870d` on 2026-09-08: `cmd/sdd/decide.go` has single-file readers/writers, `internal/dlg/collection.go` validates a collection and its archives, and `internal/hook/sessionstart.go` injects bounded bare-ID accepted entries. The user subsequently aligned on explicit config selection and planning-root storage; the previous separate repo-root selector design is withdrawn.

- **Ledger collection:** one canonical ledger plus its explicitly assigned archives, with independent local numbering.
- **Inherited source:** an explicitly bound, locally materialized parent collection, owned as source history and never mutated by SDD fork operations.
- **Fork ledger:** the selected downstream canonical file containing local decisions, fork declaration details, binding baselines and append-only reconciliation events.
- **Qualified identity:** stable collection identity plus local decision ID, independent of physical paths, remote aliases and archive filenames.
- **Effective view:** derived binding decisions, original records/provenance, replacement relationships and diagnostics; not a writable replacement ledger.
- **Basis:** retained canonical content of the approved target and relevant inheritance relationship; a mismatch makes its override stale.
- **Represented repository:** the logical owner explicitly bound by its configuration; physical storage may be a separate planning repository.

## Goals
- Separate inherited and local histories and ID allocators without moving inherited files.
- Keep root-file footprint to the existing planning configuration; reuse planning-root `Decisions/` storage.
- Preserve exact-text approval, collision reconciliation, append-only history and review isolation.
- Make every decision-aware consumer agree on authority, historical identity and unresolved conditions.
- Reconcile only relevant source changes, while ordinary newly effective constraints still receive collision checks.

## Non-Goals
- Repository/module migration, link replacement, import rewriting or rewriting historical planning evidence.
- Implicit inheritance, last-writer-wins, semantic merging, partial statement patches or automatic successor rebasing.
- Remote policy services, fetching/cloning, live sibling checkouts, remote mutation or authenticated remote provenance.
- Multiple parents, sibling-fork merging, scope remapping or automatic SCM merge-conflict repair; single-parent chains remain in scope.
- New persistent repo-root selectors/ledgers/directories, permanent complete-generation trees, or requiring a source-repository commit for externally stored ledger bytes. Short-lived atomic replacement files are not policy storage and must be cleaned after success/rollback or explicit crash recovery.
- Plan-graph state/closure changes, dashboard work, or expanded ledger access for intent-isolated reviewers.

## Requirements

### Functional Requirements
- **FR-01**: **Explicit config selection.** Add a versioned declaration in the represented repository's existing `planning-config.json`, explicitly selecting fork mode, planning-root-relative ledger path, stable ledger identity and represented-repository identity. Resolve that path against the configured planning root, whether inside or outside the repository. A remote alias, filename or nearby checkout must never imply inheritance. Without adoption/declaration, preserve legacy discovery; malformed or removed retained authority must not become silent legacy fallback. Do not create an additional repo-root policy file or directory.
- **FR-02**: **Preserve layout and collection membership.** Permit inherited canonical files/archives to remain byte-identical at their existing locations. In-repository adoption selects a sibling such as `Decisions/fork.md`; external adoption selects an explicitly repository-specific location under the external planning root. The fork file contains its own metadata and local decisions; every collection owns only its declared archives. No source renaming, renumbering, identity insertion, backlink or local append is required. Declared sources are not accidental duplicate active ledgers, but undeclared duplicates remain errors.
- **FR-03**: **Explicit local sources.** Parent bindings use a stable source identity and a portable relative locator with an explicit base: the selected planning root or represented repository. Sources must be materialized within that declared base; no live sibling or remote URL resolution. Reject missing/unreadable sources, duplicate identities, traversal and symlink/junction escape from the declared root, cycles, multiple parents and malformed declarations. Apply the same rules throughout a bounded single-parent chain; a descendant cannot hide invalid parent state. Reads never fetch, copy, update or write source files.
- **FR-04**: **Identity and ownership independent of paths.** Preserve each collection's `D-NNNN` allocator across its canonical file and archives. Qualified identities distinguish equal bare IDs in parent and child, and binding a legacy parent does not edit it. Ledger and represented-repository identities must agree between selector and selected collection; a shared external planning root must not let distinct owners accidentally share local authority. Checkout moves, archive relocation and remote renames do not change identity. Explicit identity/locator/ownership rebinding requires reconciliation.
- **FR-05**: **Citation context.** New cross-collection relations and new fork-aware artifact citations must be qualified. Existing bare references retain their source namespace; provide an explicit legacy default/context inventory so adoption does not mass-rewrite inherited artifacts. Context-free ambiguous references fail, never prefer local IDs or file order. Historical lookup returns the original record and separately identifies any effective replacement; it never rewrites historical evidence to cite the replacement.
- **FR-06**: **Deterministic applicability.** Resolve the parent first, then local accepted decisions and only explicit accepted current overrides. Proposed/rejected/superseded local entries cannot suppress a parent. Retain history and rejected alternatives for audit/collision workflows. Preserve original source statuses and report effective applicability separately. File order, dates as priority and model judgment cannot select authority; ended overrides must not reappear as unlinked local binding constraints.
- **FR-07**: **Whole-decision overrides.** Target one qualified accepted decision effective in the immediate parent's view. Require a complete standalone replacement statement, rationale, full scope, explicit confirmation and target basis. Deliberately retain or replace confirmation; surviving obligations must be restated and reviewed. No inferred word/field substitution. Two effective replacements for the same target are an error even if their scopes appear disjoint. A child cannot target an already-hidden ancestor to bypass parent resolution.
- **FR-08**: **Exact approval and collision discipline.** Adoption, selector retargeting, source/owner rebinding, accepting/reconciling/restoring overrides and detachment require explicit reconciliation and approval of the exact complete persisted change before an agent writes it. Approval of an idea is not approval of its record. Unlinked conflicts remain collisions. Checks include the target, other effective constraints, relevant proposals/rejected alternatives and existing scope/related overlap semantics. Deterministic candidates remain distinct from semantic judgment; one-way conflicts escalate under the existing convention.
- **FR-09**: **Append-only local lifecycle.** Supersession reciprocity and accepted-entry immutability remain local to each collection. Override relations are separate cross-collection relationships without parent backlinks/status edits. Changing an accepted replacement/basis appends approved local history; a successor has no inherited override authority without its own explicit relation/basis. Restoration is an approved append-only event preserving the former override. Deleting fork metadata or selector configuration cannot silently erase known authority history.
- **FR-10**: **Versioned basis comparison.** Retain old canonical target content and relevant relationship information for offline explanation. Compare all schema-supported decision-bearing fields, including statement, scope, rationale, rejected alternatives, confirmation, reversibility, status, supersession and extension fields. Formatting, comments, key order, ledger timestamps, unrelated entries and archive movement alone do not stale a basis. Do not use a whole-ledger digest for override freshness. Specify versioned canonicalization before implementation; unsupported versions cannot be treated as current.
- **FR-11**: **Selective reconciliation.** Target edits/removal/rebinding/ineffectiveness/supersession stale the affected override; show old basis, current target, local record and available successor lineage. Never transfer authority to a successor or silently restore the old parent statement. Unrelated compatible changes need no local metadata rewrite, but newly effective conflicting decisions still create ordinary collision candidates. Source-integrity failures remain invalid even when the defective entry is not overridden.
- **FR-12**: **Unresolved authority blocks reliance.** Missing/invalid sources and stale/ambiguous relationships yield complete machine-readable diagnostics and an invalid or reconciliation-required view. Inspection may show old/current records but neither as a clean resolution. Structural/stale authority fails fork validation. Semantic candidates keep existing non-gating severity but require judgment before contradictory work. Affected/global/unresolvable scopes block reliance conservatively; source-integrity failures invalidate the whole view, and ancestor failures propagate.
- **FR-13**: **Shared CLI/validation surface.** Effective/history/qualified lookup/diagnostic reads and existing list/search/add/focused/root validation share selection and resolution. Every mutation targets the selected local collection/configuration, never sources. Versioned structured output includes qualified/source identity, original status, applicability, relationships/basis and severity; raw history is explicitly non-effective. Filters cannot hide authority failures. Structural/stale findings exit 1, malformed/could-not-run conditions exit 2, candidates-only success exits 0 with guidance.
- **FR-14**: **Complete consumer migration.** Migrate convention, lifecycle capture/consultation, ad-hoc skill, manual `/decide` including `/decide check`, history/archive/hygiene operations, researcher, intent-aware reviewers, onboarding/post-compaction, graph decision/intent readers and SessionStart. Each required consumer uses the resolved view or explicitly refuses unsupported fork mode. Hooks stay nonfatal and preserve unconfigured missing-ledger/missing-binary no-ops; configured failures emit warnings, not partial authoritative instructions. Warnings and full-read notices survive context truncation. Preserve intent-isolated lane exclusions and canonical/portable agreement.
- **FR-15**: **Scope and external storage isolation.** Interpret inherited repository-relative applicability against the consuming repository's corresponding layout while retaining original scopes in provenance. Missing scopes require reconciliation; no automatic irrelevance or path remapping. An approved complete local replacement can supply changed scope without hiding source-integrity errors. Global means global to the represented repository, not every repository sharing a planning root. Related-artifact overlap uses the same context. External ledger history belongs to its planning store/versioning system; the source config is a selection/ownership binding, not evidence that ledger bytes were committed in the source repository.
- **FR-16**: **Safe writes and recovery.** Preview exact local/config files, bytes, authority deltas and dependency digests. Recheck before publication and refuse stale inputs. Keep ordinary local changes in the single fork file where possible. For adoption, retargeting or archive operations spanning configuration and ledger files, including different filesystems, guarantee prior complete authority, new complete authority or explicit recovery-required state—never partial authority labeled valid. Clean reported rollback leaves pre-operation bytes; post-publication ambiguity is reported separately, not as guaranteed rollback. Specify crash/interruption, lost reply, source publication-window changes and explicit recovery. Reads do not recover or acknowledge basis changes. Preserve inherited bytes and unrelated work; store transaction support under the planning root, not new repo-root files.
- **FR-17**: **Compatibility and capability.** Never-adopted repositories retain existing discovery, bare-ID behavior, lifecycle, diagnostics and approval gates. Expose supported fork/schema/canonicalization/transaction capabilities for setup/skills to check before reliance; old binaries/plugins are not fork-safe. Extend config schema, ledger schema/templates, validators, hooks and generated guidance together. Preserve frozen legacy verdicts and add fork fixtures. Document external planning-history commits separately from source-config commits without automatically committing either.
- **FR-18**: **Observable source continuity.** Initial approval binds identity, explicit-root relative source locator and an immutable canonical baseline of collection records/lifecycle relationships. Retain enough content for local comparison without fetching historic revisions; keep it separate from override bases. Subsequent reads preserve baseline identity/history under existing lifecycle rules, allow compatible additions/archive moves and use available repository history. Declared rebinding or incompatible replacement/removal requires new approved binding history and re-reconciliation of dependent bases, even if the identity string stays the same. Equivalent content substitution is indistinguishable and is not authenticated provenance. For external sources, inspect their actual planning-store history where available, not the represented repository's unrelated history.

### Non-Functional Requirements
- **NFR-01**: Identical configuration, materialized collections/history and supported versions produce identical identities, applicability, basis comparisons and ordered diagnostics across processes. Traversal terminates with explicit cycle/depth/version failures, never silent truncation.
- **NFR-02**: Reads/hooks/validation are offline and leave tracked/untracked bytes unchanged, including no recovery or read-created support files. No upstream credentials or live checkout dependency. Cross-filesystem mutation recovery is explicit and testable.
- **NFR-03**: Native Windows/macOS/Linux path handling, with portable relative locators and explicit root anchors. Reject private/credential-bearing source addresses and unintended root escapes. Fixtures contain no private host/account/repository identity. Do not retain new repo-root policy/support artifacts beyond changes to the existing planning configuration. Per-file atomic replacement may use operation-owned transient files beside the target; they never select authority and must be removed after success/rollback or explicit interruption recovery. Locks and journals remain under the planning root.
- **NFR-04**: Every suppressed inherited decision traces to an accepted current local override and basis; every invalid/stale relationship identifies affected records and inspection/reconciliation action. CLI output is complete; hooks may summarize with warnings retained. Describe external versioning and transaction outcomes honestly.
- **NFR-05**: Add Good/Bad and integration fixtures for adoption, composition, citations, lifecycle, consumers, upstream changes, external roots and interruption. The eventual implementation passes `make test`, frozen legacy regression, schema/template, generated drift/leak and native path/security gates. Document authoring does not claim implementation success.

## User Stories
- As a maintainer, I want to add a selected sibling fork ledger without editing inherited history or adding another repo-root file.
- As a user with external planning, I want my existing repository configuration to identify my decision authority without mixing it with other repositories' ledgers.
- As an agent, I want one effective view of approved local replacements and inherited constraints, with historical references preserved.
- As a maintainer merging upstream, I want targeted reconciliation only where approved authority changed, while new unrelated conflicts still receive judgment.
- As a reviewer, I want complete provenance and no leakage of ledger intent into isolated lanes.
- As a non-fork user, I want no migration or new files.

Covers FR-01, FR-02, FR-16.
- [ ] **AC-03**: Equal parent/child local IDs resolve through qualified identity; local allocation includes only local canonical/archives; same-collection duplicates fail. Legacy bare citations retain their declared source context without mass rewrite, new ambiguous references fail, and archive movement preserves identity. Covers FR-04, FR-05.
- [ ] **AC-04**: Approve a complete generic SDD-Toolchain:pd-f4a8d1a2-shaped replacement changing repository/module identity while retaining `/v2`, user installation, no plugin compilation/download and the version floor. Its explicit fixture-backed confirmation checks retained/new obligations, not the old identity. Effective readers bind the replacement; no source/backlink/import/link edits occur. Covers FR-06, FR-07, FR-13, FR-14.
- [ ] **AC-05**: Proposed/rejected/unlinked/colliding-ID records do not suppress inherited decisions. Duplicate current override targets fail; an explicit override cannot exempt a conflict with another effective constraint. Covers FR-06, FR-07, FR-08.
- [ ] **AC-06**: Unapproved/stale-digest writes refuse. Approved acceptance, explicit local successor and append-only restoration preserve accepted statements/bases and source bytes. A successor without explicit authority cannot silently continue suppression. Known committed history cannot be erased by a recovery rollback. Covers FR-08, FR-09, FR-16.
- [ ] **AC-07**: Compatible unrelated append/status changes, formatting, metadata and archive movement leave current bases/local bytes untouched and add newly effective constraints. An unrelated conflict creates a candidate; invalid accepted-history mutation invalidates the source/view. Covers FR-10, FR-11, FR-18.
- [ ] **AC-08**: Independently mutate each decision-bearing target field, remove/supersede it or rebind identity; each relevant case stales the override, preserves old basis, exposes current/lineage context and blocks clean authority. No automatic refresh or successor transfer. Covers FR-10, FR-11, FR-12.
- [ ] **AC-09**: Reconciliation displays old/current content and exact new local history, refuses missing approval/concurrent changes, and appends only approved current basis. Another source change makes it stale again. Covers FR-08, FR-10, FR-11, FR-16.
- [ ] **AC-10**: Missing/unreadable source, identity collision, cycle/multiple parents, duplicate IDs, unsupported versions/depth and escape from either explicitly declared root fail without reads mutating state. A valid three-level chain resolves; stale/invalid ancestors remain blocking. Covers FR-03, FR-04, FR-10, FR-12; NFR-01 through NFR-03.
- [ ] **AC-11**: All required consumers, including `/decide check`, graph intent and onboarding, agree on effective identities and diagnostics. Over-budget hooks retain warnings/full-read instructions; unresolved hooks remain nonfatal but never present partial authority as complete. Isolated lanes receive no extra ledger context. Covers FR-13, FR-14; NFR-04.
- [ ] **AC-12**: Global/nested/related-connected/missing/relocated scopes use consuming-repo semantics. Two owners in one external planning root cannot accidentally select each other's ledger; identity/owner mismatch fails, and unrelated repository reads/writes remain unchanged. An external ledger commit is not claimed to be a source-repository commit. Covers FR-04, FR-08, FR-15.
- [ ] **AC-13**: Snapshot all relevant tracked/untracked bytes; reads remain unchanged. Inject concurrent source/local/config changes, errors/crashes before and after every multi-file publication point, cross-filesystem failure and lost replies. Readers see old/new complete or recovery-required state; clean rollback restores old bytes, ambiguous outcomes are explicit, and read paths never repair or activate staged authority. Covers FR-03, FR-16; NFR-02.
- [ ] **AC-14**: Verify complete structured identities/provenance/applicability/history and diagnostic order. Structural/stale exit 1, could-not-run exit 2, candidates-only exit 0 with judgment guidance. Filtering cannot hide failures; updated workflows reject unsupported binaries before reliance. Covers FR-12, FR-13, FR-17; NFR-01, NFR-04.
- [ ] **AC-15**: Eventual `make test` passes with new fork fixtures, unchanged legacy expectations, synchronized config/ledger schemas/templates/conventions and regenerated portable trees. Native path/recovery tests pass; fixture content is portable and non-private; no extra repo-root support artifacts appear. Covers FR-17; NFR-03, NFR-05.
- [ ] **AC-16**: Approved bindings retain offline baselines. Compatible evolution preserves continuity; deleting/replacing baseline history or changing root/locator/identity requires reconciliation. Explicit rebinding appends a new record and invalidates dependent bases. Equivalent source substitution never becomes an authentication claim. Test sources under both declared roots and unavailable historic remote revisions. Covers FR-03, FR-04, FR-10, FR-16, FR-18.

## Constraints
- This is a proposed implementation contract, updated after the user's alignment on config-selected authority and planning-root storage. It does not activate fork mode or modify the real ledger/configuration.
- Preserve SDD-Toolchain:pd-9dce9845's convention/skill/manual coverage, SDD-Toolchain:pd-bac0b279's collision stops and SDD-Toolchain:pd-eed0dbed's exact-text approval. Applying an unchanged approved override is not a new automatic semantic resolution.
- **ForkAwareDecisionLedgers:pd-764da52e governs selection and storage:** the user approved and recorded explicit config-selected authority with planning-root storage, including independently versioned external ledgers. Preserve logical repository ownership and reject accidental global authority; do not pretend an external ledger is versioned with source code. Future adoption, overrides and authority changes still require their own exact-text approval under SDD-Toolchain:pd-eed0dbed.
- SDD-Toolchain:pd-f4a8d1a2 remains binding for upstream; its motivating downstream override is a generic future fixture. Preserve SDD-Toolchain:pd-5ea9a4ae's generated distribution and SDD-Toolchain:pd-f98234fe/SddGraph:pd-b9031144/SddGraph:pd-312da877 review/completion/tracking guarantees. SddGraph:pd-2c12dec8 still governs boundary bookkeeping.
- Exact changes to source config and external planning history require separate native-SCM identities when recorded; no automatic commit, submit or publishing follows from a local transaction.
- Nothing in this spec authorizes inferred accepted ledger text or altering isolated reviewers' context.

## Dependencies
- `Designs/ForkAwareDecisionLedgers` defines `decisionLog` serialization, collection/owner identity, basis canonicalization, events and single-/multi-file publication/recovery.
- Normative shared decision/frontmatter/path/orchestration/review conventions, lifecycle commands, decision skills and agent definitions must change together.
- Existing entry points include `cmd/sdd/decide.go`, config/store, `internal/schema/decision-log.json`, `internal/dlg`, `internal/rules`, `internal/hook/sessionstart.go` and graph decision/intent readers. This is not an exhaustive file inventory.
- Platform filesystem contracts used by the design are pinned there. No third-party remote API, hosting endpoint, service or upstream network access is required.

## Open Questions
- Diagnostic numbering — **non-blocking** — Behavior and severity are fixed; implementation allocates unused codes against the live registry without changing the contract.
- External planning history tooling — **non-blocking** — Use the actual configured planning store's native history when present and report unavailable history honestly; selection, ownership and retained approval baselines do not depend on a particular hosting service.
